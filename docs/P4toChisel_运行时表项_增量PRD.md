## 0. 背景与变更范围

当前 P4C 表实现为 `const entries` **静态融合**：条目在编译期烘成 MuxCase 组合逻辑（`ChiselBackend.emitStaticTable`），运行时不可更新。这是设计文档 §4.3 / §8 明确的后续方向——表存储走 `BaseCbb/memory` 封装。

本 PRD 定义**运行时可配置表项**增量：生成的表模块支持运行时写入/更新表项，查找在运行时按当前表内容匹配（key → action/参数的映射是运行时状态，不是编译期常量）。这是 v1model 实用化（控制平面软件下发表项）的关键一步。

- **不变部分**：key 构建、hit 比较、action 执行的 MatchPlan 结构；切拍 valid 链契约（`docs/P4toChisel_切拍_增量设计.md` §1.3，发起间隔 ≥ N）不受影响；
- **变更部分**：表存储从编译期 MuxCase 常量 → 可写存储（介质选型 Vec 寄存器 vs BaseCbb SRAM 由架构师裁定，PRD §3 给建议）；新增写接口；P4 语法层需要一种标记"该表为运行时表"的方式（形态见 §6 待确认）；
- **零回归底线**：未标记运行时的表（`const entries`）行为与现状**逐字节一致**。

## 1. 产品目标

1. 让控制平面能在运行时对生成的表模块下发/更新表项，硬件查找按当前表内容命中，无需重新综合或重新生成 RTL——表从"编译期数据"变为"运行时状态"。
2. 运行时表是**可选增量能力**：显式标记才启用；静态表（const entries）保持现状零回归，同一 control 内两种表可共存。
3. 为后续 BaseCbb SRAM/TCAM 资源映射与完整 v1model 表 API 预留存储抽象边界（介质与接口协议可在抽象层后替换）。

## 2. 用户故事

1. **As a** 控制平面软件工程师，**I want** 通过写接口下发"key → action(参数)"表项，**so that** 后续报文按最新表内容命中，业务变更无需重新综合。
2. **As a** 硬件工程师，**I want** 查找进行中发生表项写入时，该次查找要么命中旧值要么命中新值、绝不输出撕裂的中间值，**so that** 转发行为不因配置更新而错乱。
3. **As a** 硬件工程师，**I want** 未标记运行时的表保持静态融合、生成代码不变，**so that** 现有 5 个 demo 与 76/76 P4C 测试零回归。
4. **As a** 验证工程师，**I want** 用 chiseltest 驱动写接口后立刻发起查找，断言命中/未命中与动作参数正确，**so that** 运行时正确性有可自动化回归的用例。
5. **As a** SoC 集成者，**I want** 表深、key 宽度、action 参数宽度在编译期固定并由生成代码头部注释写明，**so that** 上位机/固件按已知地址空间编程。

## 3. 需求池

优先级定义：P0 = 必须有（本迭代交付）；P1 = 应该有（紧随其后）；P2 = 可以有（后续）。

### P0（Must have）

| # | 需求 | 说明 |
|---|------|------|
| P0-1 | **运行时可写表存储** | 表条目存于可写存储，编译期只固化"结构"（表深、key 宽、action 编号与参数宽度），不固化内容。介质选型**留给架构师裁定**，PM 建议：初版用 `Vec[Reg]`（组合读，最贴近现有 MuxCase 查找模式，查找路径零拍增加、valid 链无需改造）；`BaseCbb` SRAM 封装作为 P2 资源映射路径（同步读引入 1 拍时延，需流水化查找，见 §6-Q3）。 |
| P0-2 | **写接口** | 生成模块暴露表项写能力（端口/协议形态——每表独立写端口 vs 共享写总线、是否引入独立配置时钟域——留给架构师）。硬性要求：① 单表项更新**原子**（单拍提交或明确协议）；② 写与查找并发时的可见性语义明确（下一条查找看到旧值或新值，禁止撕裂）；③ 非法写（地址越界）不破坏表内容。 |
| P0-3 | **查找功能正确性（写入后）** | 写入新表项后查找命中并执行对应 action（含参数）；覆盖：空表全 miss（走 default）、新增命中、更新已有项（旧值不再命中/命中新动作）、覆盖后恢复。default 行为保持编译期固定（是否允许运行时改 default 见 §6-Q4）。 |
| P0-4 | **静态模式零回归** | 未标记运行时的表仍走 `emitStaticTable` 现有路径，`const entries` 行为与现状逐字节一致（`diff -r generated/p4c` 基线为空）；76/76 P4C、357/357 全仓测试绿。 |

## 4. 非目标（明确不做）

1. **不做 TCAM 资源映射与硬件优先级编码**（lpm/ternary 的真 TCAM 路线）；设计文档 §4.3 的"TCAM + 优先级编码"仅作为远期方向记录。
2. **不做完整 v1model 表 API**（entry priority、TTL/老化、idle timeout、meter 关联）——只做"写 key→action 映射"这一层。
3. **不做控制平面软件栈/驱动**：只交付硬件写接口及其协议约定，上位机实现不在本期。
4. **不接 BMv2 对照**：正确性验证以 chiseltest 写入→查找闭环为准（与切拍增量同口径）。
5. **不做表项批量原子更新**（多表项一次事务提交）：本期写粒度为单表项。
6. **不改变既有切拍契约**：发起间隔 ≥ N、valid 单拍脉冲、Sink 固定末级等约定原样沿用，运行时表不得引入违背该契约的结构。

## 5. 验收标准

1. **静态零回归（P0-4）**：不标记运行时表时，`sbt clean compile` 后 `diff -r generated/p4c <基线>` 逐字节为空；P4C 76/76、全仓 357/357 绿。
2. **运行时正确性（P0-3）**：新增运行时表 demo（建议 `p4/demos/demo7-runtime-table.p4`），chiseltest 覆盖：① 写入后命中并执行对应 action 与参数；② 空表全 miss 走 default；③ 更新已有项后旧动作不再出现；④ 地址越界写不改变表内容；⑤ 写接口时序与协议在生成代码头部注释写明。
3. **并发语义（P0-2）**：写入期间发起查找，断言结果为旧值或新值之一（不依赖内部实现的具体拍序），无撕裂输出；该语义写入生成文件头注释。
4. **混用（产品目标 2）**：同一 control 内静态表 + 运行时表共存，编译通过且各自行为正确。
5. **编译期校验**：运行时表不允许携带 `const entries`（报 `P4Error`，信息含表名）；表深/key 宽/action 参数宽编译期固定并回显在日志中。
6. **新增用例门禁**：新增 Spec 全绿，测试计数从 76/76、357/357 基线只增不减。

## 6. 待确认问题（需主理人/架构师拍板）

1. **默认模式与切换方式**：默认保持静态（推荐，与切拍增量 D4 的零回归策略一致）；"运行时表"的标记用 (a) P4 注释编译指示（如 `// p4c: table cls_table runtime`，与既有 `// p4c: stages=N` 惯例统一）还是 (b) 生成器参数（按表名列表）？推荐 (a)，请确认。
2. **存储介质（P0-1 决策权在架构师）**：初版 `Vec[Reg]`（组合读，PM 推荐）vs 直接上 BaseCbb SRAM（同步读 + 1 拍）？若选寄存器，P2 SRAM 映射是否要求本期就预留存储抽象 trait？
3. **SRAM 同步读与切拍 valid 链衔接**（若最终选 SRAM）：查找读出滞后 1 拍后，hit/action 相对 `io.valid` 延迟 1 拍——是 (a) 把表读当作流水第 1 级并入现有 valid 链（查找整体 +1 拍），还是 (b) 引入独立查找握手？涉及下游时序契约变化，需明确。
4. **default entry 是否允许运行时改写**：v1 建议编译期固定 default action、仅表项运行时可写（少一个运行时状态、语义简单）；若用户需要 default 可改，写接口协议需扩展。请确认本期范围。
5. **写接口形态与并发可见性承诺**：每表独立写端口 vs 共享写总线（P2-2 提前）；写时钟域与查找同域即可，还是必须预留独立 config 时钟域？"写后下一条查找可见"（推荐）还是"写后同拍查找可见"（需要旁路）？
