# P4 → Chisel 切拍功能 增量 PRD

版本：v0.1（增量，基于 P4toChisel_设计文档.md v0.2 / M1~M5 已实现）
作者：许清楚（产品经理）
状态：待评审

---

## 0. 背景与变更范围

当前 P4C 将 ActionDAG 全组合单拍发射：control 的 action / 静态融合表 / parser 各状态的提取逻辑，全部生成为一段组合逻辑，在单拍内完成。当 DAG 关键路径过长（深算术链、宽 MuxCase）时时序无法收敛，且用户没有任何手段干预。

本 PRD 参考 Google XLS 的调度思想，增加**按拍数预算切分 DAG**的调度 pass，并在 Chisel 后端按级发射：级间插寄存器、valid 信号逐级传递、sink 在末级且 valid 有效时生效。范围覆盖三处：

- **Action**：control 内直行 action 的 ActionDAG 切拍；
- **Control**：表匹配（key 构建 + hit 比较 + action 执行）整体切拍；
- **Parser**：FSM 单个状态内的报文窗口提取逻辑（移位 + 多字段切片）切拍。

实现落点（对照现有代码）：
- `Ir.scala`：`Node` 目前无调度信息 → 新增调度结果（节点 → 拍级映射），不破坏现有不可变 DAG；
- `Passes.scala`：在 `runAll`（constFold/cse/dce）之后新增 `schedule` pass；
- `ChiselBackend.scala`：`Emitter` 目前递归内联为组合表达式 → 改为按级分块发射，级间插 `RegEnable` + 逐级 valid；
- `Generate.scala` / CLI：拍数预算参数入口。

## 1. 产品目标

1. 让硬件工程师能通过**拍数预算**控制生成模块的关键路径长度：给定预算 N，编译器把超深组合 DAG 自动切分为 ≤N 拍的多级流水，功能与单拍版本等价（仅延迟不同）。
2. 切拍是**可选增量能力**：默认不开启时，生成代码与现状完全一致，现有 5 个 demo 与全部测试零回归。
3. 为后续 XLS 式完整调度（延时模型、频率约束驱动）打好 IR 与后端的结构基础（调度信息显式化、Emitter 分级发射框架）。

## 2. 用户故事

1. **As a** 硬件工程师，**I want** 给 action 的 DAG 指定拍数预算 N，**so that** 生成的 Chisel 把计算切成 N 级、每级之间有寄存器，关键路径缩短到可收敛。
2. **As a** 硬件工程师，**I want** 多拍流水只在 valid 链有效时才更新输出和状态单元（寄存器/计数器），**so that** 无有效数据流经时不会产生虚假的寄存器写或计数器累加。
3. **As a** 硬件工程师，**I want** 对整条 control（表匹配 + action 执行）切拍，**so that** 宽表 MuxCase 和 action 计算的总路径被分摊到多拍。
4. **As a** 硬件工程师，**I want** 对 parser 某个 FSM 状态内的提取逻辑（大位宽移位 + 多字段切片）切拍，**so that** 单状态内深提取路径不再成为时序瓶颈，同时 FSM 状态机结构本身保持不变。
5. **As a** 硬件工程师，**I want** 用同一组报文激励分别打单拍版和多拍版生成模块，比对末拍输出一致，**so that** 我能确信切拍只改变延迟、不改变功能。

## 3. 需求池

优先级定义：P0 = 必须有（本迭代交付）；P1 = 应该有（紧随其后）；P2 = 可以有（后续）。

### P0（Must have）

| # | 需求 | 说明 |
|---|------|------|
| P0-1 | **ActionDAG 切拍 pass（按级数预算）** | `Passes` 新增 `schedule(dag, budget)`：拓扑序遍历，将节点分配到 0..N-1 级；预算 N≥2 时启用切拍，N=1/缺省保持全组合。调度结果为节点→拍级映射，不修改 DAG 本身（与现有 pass 的不可变约定一致）。 |
| P0-2 | **生成代码按级发射 + valid 逐级传递** | ChiselBackend 按调度结果分级发射：第 0 级读 `io.*In`，第 k 级（k>0）读第 k-1 级经寄存器（`RegEnable`，使能 = 上一级 valid）传递的值；`stageValid` 寄存器链逐级传递；`OutputWrite` / `RegWrite` / `CounterAdd` 等 sink 仅在末级且 `stageValid(N-1)` 有效时生效（stateful 场景与现有 `io.valid` 取与）。 |
| P0-3 | **功能等价回归** | 新增切拍等价性测试：同一 P4 程序生成单拍版与 N 拍版，chiseltest 相同激励序列（覆盖报文→输出字段 + 寄存器/计数器终值），多拍版在 N-1 拍延迟后输出与单拍版逐一相等。现有 P4C 22 tests / 全仓 307 tests 在默认（不切拍）模式下零回归。 |

### P1（Should have）

| # | 需求 | 说明 |
|---|------|------|
| P1-1 | **Control 整体（表 + action）切拍** | 静态融合表路径（key 构建、hit 比较、MuxCase 输出选择、entry action DAG）纳入统一调度：第 0 级 key 构建，后续级完成比较与 action 计算。hit 信号与 action 数据同流水，default/透传路径保持语义。 |

## 4. 非目标（明确不做）

1. **不做 parser FSM 结构改造**：不把 FSM parser 改造为流水线 parser / FPP 风格固定窗口流水线（那是设计文档 §4.2 的另一条路线，独立立项）。
2. **不改表存储架构**：静态融合（const entries 烘焙 MuxCase）方式不变；不做运行时可配置表、SRAM/TCAM 资源映射（设计文档已列为后续工作）。
3. **不接 BMv2 行为对照**：等价性验证仍以"单拍版 vs 多拍版生成模块互测"为准，BMv2 对照是独立事项。
4. **不做频率约束闭环**：不接受目标频率（MHz）输入自动反推拍数——本迭代预算以"拍数"为单位，由用户显式给出。
5. **不做跨 action / 跨语句的 DAG 合并调度**：切拍以单个 ActionDAG（一个 action 实例 / 一条 apply 直行语句 / 一个表 / 一个 parser 状态）为边界，不跨边界重排。

## 5. 验收标准

1. **默认零回归**：不传拍数预算时，5 个 demo 生成代码行为不变，P4C 22/22、全仓 307/307 绿。
2. **切拍正确性（Action，P0）**：对 demo1（组合 action）与 demo4（Register/Counter extern）生成 N=2/3/4 拍版本：
   - 生成代码中可见 N-1 组级间寄存器与 N 级 `stageValid` 链；
   - 相同激励序列下，输出字段与寄存器/计数器终值与单拍版一致（容忍固定 N-1 拍延迟）；
   - valid 为低期间，无任何寄存器写 / 计数器累加发生（chiseltest 断言）。
3. **Control 切拍（P1）**：demo2（exact 表静态融合）切 N 拍后，各表项命中/未命中场景的输出与单拍版一致，hit 与 action 数据同步到达末级。
4. **Parser 切拍（P1）**：demo3/demo5 的 parser 状态内提取逻辑切拍后，FSM 状态跳转序列与解析结果（header 字段 + valid 位）与单拍版一致，总解析拍数增加可预期（= Σ 各状态内增加的级数）。
5. **端到端（P1）**：demo5 Top 在 control 切拍后，`outValid` 及输出在 parser done 后的固定拍数处出现，下游时序契约在生成代码头部注释中写明。
6. **报错清晰**：预算 N 非法（<1）或 DAG 无法满足约束时，编译期报 `P4Error`，错误信息含 DAG 名与原因，不静默降级。

## 6. 待确认问题（需用户/架构师拍板）

1. **拍数预算的给出形式**：三选一或组合——(a) CLI/构建参数全局默认（如 `P4cMain in.p4 out/ --stages 3`）；(b) P4 源内注释编译指示（P2-2 提前）；(c) 按 control/parser 分别配置。默认推荐 (a) 起步、预留 (b) 接口，请确认。
2. **切分策略**：第一版是否接受"按拓扑深度均匀切分"（每级节点数/深度大致均分），延时模型（P2-1）后置？若用户对某条路径有明确时序瓶颈认知，是否需要本迭代就支持指定"哪几个节点必须落第 0 级"？
3. **状态单元读写时序语义**：单拍版中 RegRead 读旧值、RegWrite 同拍生效；切拍后 RegRead 落第 0 级、RegWrite 落末级，中间若干拍寄存器呈"半更新"窗口——(a) 声明不支持同 DAG 内先读后写同一寄存器（报错），还是 (b) 增加写旁路（末级写值前递给读）？(b) 改变可观测时序，需明确取舍。
4. **demo5 Top 的 outValid 语义**：control 切拍后 `outValid = RegNext(fire)` 不再对应输出有效时刻。是否允许将其改为"末级 stageValid"（接口时序变化、延迟增加 N-1 拍），还是保持现语义并新增 `outDone` 信号？涉及下游使用方，需用户确认。
5. **接口变更容忍度**：无 extern 的纯组合 control 目前无 `io.valid` 输入；切拍后必须引入 valid 才能逐级传递。接受"切拍模式下生成模块新增 valid 输入端口（不切拍则不加）"这种按需端口差异，还是要求所有生成模块统一带 valid（现有测试与使用方需同步修改）？
